A playbook for using AI agents safely in data engineering

Guardrails over intelligence: the value is in the constraints, not the model.

There's a lot of noise right now about AI agents writing data pipelines. Most of what I see is a demo: someone hands a language model database access, it generates some Spark, and it works on the happy path. That's a party trick, not engineering, and I wouldn't run it in production.

This post is about the opposite approach. The interesting problem isn't making an agent smart enough to write a correct pipeline from scratch. It's shrinking the problem until the agent can't get it dangerously wrong. You do that with a fixed architecture, a catalog of pre-tested building blocks, a contract that bounds the task, and human gates at the points that matter. In one line:

We don't make the agent smarter. We shrink the problem until it can't be dangerously wrong. Humans design the constraints, agents operate within them, humans hold the gates.

Everything below is an instance of that idea.

What gets decided up front

Before any agent runs, people decide the parts that must not vary:

  • The global architecture. A layered lakehouse: raw / bronze / silver / gold, or landing / bronze / curated. The names don't matter much, the discipline does. Each layer has a fixed contract about what it holds and how much you can trust it.
  • The abstraction layer. A library of tested classes the agent composes, instead of raw Spark it makes up.
  • The deployment path. Terraform and a CI pipeline, written by people, that validate, test, and promote between environments.

The agent is almost a detail. The tested abstractions and the enforced structure are the real product. The agent is just a fast, tireless way to wire them together from a spec.

The raw zone

The raw zone is where sloppy design hurts the most later, because every layer above it inherits its shape. It's also the part an agent should touch least, since the decisions here are architectural, not per pipeline. A person makes them once and the platform enforces them from then on.

Two rules make a good raw zone: it's immutable and append-only, and it's partitioned by ingestion time.

Immutability is your replay backstop. If a transform has a bug, you re-derive every downstream table from untouched raw. Nothing is lost, and raw stays a byte-for-byte record of what the source actually sent. You never update or delete in raw; you only append.

The subtler choice is partitioning by ingestion time (when you received the data) rather than event time (when it happened at the source):

raw/source=salesforce/dataset=orders/ingest_date=2026-01-15/hour=14/

You control ingestion time, and it only moves forward. Event time doesn't. Events arrive late and out of order: a mobile client buffers offline for three days, then sends a batch with old timestamps. If raw were partitioned by event date, that batch would force you to reopen and rewrite old partitions, which is messy and not idempotent. Partitioned by ingestion date, "reprocess everything that landed on the 15th" is a clean prefix scan, and a re-run overwrites exactly one partition.

That one choice pays off in four places:

  • Idempotency. Reprocessing means replacing one partition, not rewriting the table. Write the partition atomically and a re-run produces the same result, so retrying after a failure is safe.
  • Reprocessing. Found a bug in a transform? Overwrite only the affected ingestion-date partitions, replayed from raw.
  • Backfills. Historical loads become a bounded date-range job, separate from the live pipeline, running the same code with a different window.
  • Retention and tiering. Expiring or cold-tiering old data is a prefix rule, not a row-level delete.

What you carry downstream: re-partition by event date in silver, where the business timeline matters. An event that happened on Jan 14 but arrived on Jan 16 sits in ingest_date=2026-01-16 in raw and in event_date=2026-01-14 in silver. That's why silver partitions get updated after the fact, and why silver writes are merges rather than blind appends. Ingestion time below, event time above. Get that split right and you have a platform you can reprocess, instead of one you're afraid to touch.

I'm spending time on this before the AI part on purpose. The agent is only safe if this architecture is already correct.

The abstraction layer

Here's the move that makes agents safe. We don't let agents write Spark, with each one reinventing what a bronze-to-silver step looks like. Those steps are nearly identical across pipelines anyway: read a source, standardize it, apply changes in order, enforce quality, write a table. So we write that logic once, as tested classes, and register them in a catalog the agent draws from.

RawToBronze      # land + parse + capture rescued columns
BronzeToSilver   # dedup, standardize, apply CDC/SCD
ApplyCDC         # apply an ordered change feed
ApplySCD2        # keep history with validity dates
QualityGate      # nulls, ranges, uniqueness, referential

Think about the level an agent could generate at:

  • Raw Spark. The agent can produce code that's subtly wrong, hard to maintain, and untested. Correctness lives in the agent's output, which isn't deterministic. Unsafe.
  • Calls to tested abstractions. Correctness lives in your tested class. The agent picks the class and fills in the parameters. The abstraction is the test boundary.

So the agent's job shrinks from "write a correct pipeline" to "wire known-good blocks in the right order with the right parameters". What it produces is configuration, not logic. That's the whole argument in concrete form.

The silver cleansing you always end up needing (fixing nulls, bad formats, slowly changing dimension errors) is just another abstraction here, QualityGate or Standardize, configured by the contract and never improvised by the agent.

The contract

The agent needs a bounded spec of what to build. That's the interface contract: a document a person writes, or at least reviews, describing the source, the target, and the rules. Everything downstream is derived from it, which is exactly why it's the safety boundary.

source:
  location: s3://raw/salesforce/orders/
  format: json
target:
  table: catalog.silver.orders
  primary_keys: [order_id]
  sequence_by: updated_at      # orders change events
  scd: type_2                  # keep history
  cdc: true                    # source is a change feed
schema:
  - {name: order_id,   type: string,  nullable: false}
  - {name: amount,     type: decimal(18,2)}
  - {name: status,     type: string,  allowed: [new, paid, cancelled]}
  - {name: updated_at, type: timestamp}
quality:
  - not_null: [order_id, amount]
  - unique: [order_id]

Two terms in there drive the choice of abstractions:

  • CDC (change data capture). The source emits row-level inserts, updates, and deletes instead of full snapshots. The sequence_by column orders those changes, so an older event that arrives late never overwrites a newer one.
  • SCD (slowly changing dimension). How you handle an attribute that changes. Type 1 overwrites and keeps only the current value. Type 2 keeps history: a new row per change, with validity dates and a current flag. The contract says which; the abstraction implements it.

Notice the contract uses decimal for money and is explicit about keys and the sequence column. Those are exactly the details an agent would otherwise guess, and guess wrong.

How the agent finds the abstractions

The piece people tend to skip is how the agent knows which abstractions exist and when to use each one. My answer: expose every abstraction as a described, machine-readable capability, basically a typed tool definition, and require the agent to choose only from that catalog.

Each entry carries what the agent needs to choose well: a name, a one-line "use this when", typed parameters, and preconditions (ApplySCD2 requires a sequence_by column, for example). The agent gets the contract plus the catalog and is asked for a plan: which abstractions, in what order, with which parameters. Not code.

Two properties make this safe:

  • Closed vocabulary. The agent composes only from the catalog and can't invent a transform. If a contract needs something the catalog doesn't have, the agent escalates to a person instead of improvising. I see that as the point, not a limitation.
  • Validation before generation. The plan is checked against each abstraction's preconditions before any code or Terraform is written, so a bad wiring is caught structurally rather than at runtime.

If you've built agentic systems, this is the familiar tool-use pattern: you aren't asking the model to be creative, you're asking it to pick correctly from a vetted menu. The part I'd underline is that the catalog's descriptions are a maintained part of the platform, just as much as the code they point to. If a description is vague, the agent's choices will be too.

Where the humans stand

The agent proposes; the pipeline and the people decide. Concretely, with an agentic workflow (say a Claude agent that has the abstraction catalog as its tools and opens pull requests instead of committing to main), the gates sit here:

  • Contract review. A person writes or approves the contract before anything runs. An agent can draft one from a business description, but a person signs off, because business intent is the one thing the agent must never assume.
  • Plan review. The agent proposes its plan and a person checks it: "you chose ApplySCD2 keyed on order_id, sequenced by updated_at. Is that right?" This happens before any code exists.
  • Diff review. The agent emits pipeline config and Terraform as a PR, and a person reviews the diff like any other change.
  • Tests and approval before promotion. Tests run against the produced tables, and a person approves promotion between environments. This is where you catch an agent that dropped a table or skipped a rule.
  • DAG checks. The agent generates orchestration jobs from an orchestration contract, and a person runs DAG unit tests (the kind Astronomer documents for Airflow) to make sure no job went missing.

Each gate is there to catch something specific. That's what makes them designed rather than decorative.

Here's the split of work in one place:

Layer / artifactWho does what
Raw zone designWritten by people, deterministic, fixed
Abstraction libraryWritten and tested by people
ContractWritten by a person, or drafted by the agent and approved by a person
Bronze to silver pipelineGenerated by the agent (config over tested blocks), reviewed by a person
Quality, SCD, CDC rulesDeclared in the contract, implemented by abstractions
Terraform and CIPath written by people; the agent proposes changes, a person approves, CI enforces
DAGs / orchestrationGenerated by the agent from the contract, unit-tested by a person
Gold layerWritten by people, with an assistant at most

A failure that gets through

Guardrails leak, and a post like this should say how. Here's the kind of failure that slips past everything above.

Picture a contract for a customers source that lists twelve columns. The source recently gained a thirteenth, loyalty_tier, and nobody updated the contract. The agent generates a perfectly valid pipeline: right abstractions, schema validation passes (the contract is internally consistent), tests pass (they only check the columns the contract declares). It runs green for three weeks. The problem surfaces when an analyst asks why loyalty segmentation is empty.

The agent didn't do anything wrong. It built exactly what the contract said. The gap is that nothing checked the contract against the real source schema.

The fix is another guardrail: a schema drift check that compares the live source schema to the contract at ingestion and flags differences for review, plus rescued-column capture in bronze so an undeclared field is never silently dropped. The agent is only as safe as the contract is faithful to reality, and checking that is a guardrail you have to build yourself. A smarter model wouldn't have caught this. A system-level check does.

Deployment and cost

The approval is the trigger; the CI pipeline, written by people, is the enforcement. Once someone approves the PR, CI runs the tests, shows the Terraform plan before any apply, and promotes across environments. The things you'd worry about with autonomous generation are handled by deterministic machinery that people own, not by the agent's judgment.

Cost needs its own guardrail. When pipelines are cheap to generate, "easy to generate" quietly turns into "easy to overspend". Put cost controls in the same CI path: cluster size limits through policy, and a cost estimate shown on the Terraform plan so the reviewer sees the bill before approving.

When not to use this

This isn't where you start. It pays off only where a pattern repeats and a tested abstraction for it already exists. So:

  • Young projects. Early on you don't know your patterns yet, you're still finding them. Building a catalog before you understand the shape of your pipelines is premature. Write pipelines by hand until the patterns settle, then extract abstractions, then let agents compose them.
  • One-off pipelines. If it won't be repeated, there's no abstraction, and building one for a single use isn't worth it.
  • New logic with no safe abstraction. That's why the gold layer stays human-written, with a coding assistant at most. Gold is where business logic lives. Every mart is different, so there's no repeated pattern to constrain against, the cost of a subtle mistake is highest, and there's no tested abstraction to hold the agent to.

The general rule: agents pay off where the pattern repeats and a tested abstraction exists. People own the new, the one-off, and the not-yet-understood.

The takeaway

None of this works because of a clever prompt or a smarter model. It works because the hard parts are engineered away before the agent ever runs: the raw zone is built for idempotency and replay, the transformation logic lives in tested abstractions, the task is bounded by a contract, the agent picks from a closed vocabulary, and people hold the gates where judgment matters. The agent works inside a box built so that the worst it can do gets caught.

The tools will change. The principle is the part I'd keep:

Humans design the constraints, agents operate within them, humans hold the gates.
